# 产品生命周期开发维护共识

状态：已接受

适用范围：由 Human 与多个 Agent 共同设计、开发、验证、维护或关闭的产品 Initiative。

## 目标

每个产品只解决当前生命周期阶段的问题。Agent 根据当前阶段、当前假设和退出证据判断工作是否值得做；后续阶段的可靠性、规模化和治理事项保留为 Deferred，不提前变成当前工作量。

## 单一阶段声明

产品当前阶段只在所属 Initiative 的 active Spec 或 Plan 中声明。ZInitiatives 只保存导航，不复制阶段细节。

阶段声明至少包含：

```text
Current stage:
Current product hypothesis:
Current vertical slice:
Stage exit evidence:
Deferred decisions:
```

阶段变更是 Human 决策。Agent 可以基于证据建议晋级、停留、回退或终止，但不能自行改变阶段。

## Agent 工作协议

Agent 开始产品工作时：

1. 从 ZInitiatives 找到所属 Initiative、active Spec 和 Plan。
2. 读取阶段声明，确认当前产品假设、纵向切片和退出证据。
3. 将拟做工作归入下列一种：
   - `stage-critical`：当前纵向切片或退出证据不可缺少；
   - `observed-failure`：修复当前实验已经复现、且阻止有效验证的问题；
   - `deferred`：服务未来阶段，当前没有产品证据要求。
4. 执行 `stage-critical` 和获得 Human 接受的 `observed-failure`；把 `deferred` 记录到 active Spec 或 Plan，不展开设计或实现。
5. 完成后记录可观察结果，并判断它是否改变当前阶段的退出证据。

Agent 不能说明一项工作与当前纵向切片、退出证据或已复现失败的关系时，该工作默认属于 `deferred`。

## 全阶段底线

所有阶段都遵守最低安全边界：不泄露凭证，不执行未经授权的不可逆操作，不把真实敏感数据暴露给未受控系统，不绕过明确的权限要求。

最低安全边界不等于生产级安全建设。认证体系、细粒度 ACL、HA、灾难恢复、完整审计和合规设计，只有在当前阶段的真实使用范围或退出证据要求时才进入工作范围。

语义正确性属于产品验证，而不是可靠性加固。若纵向切片要验证唯一 claim，则最小实现必须真的排除重复 claim；它不必同时解决跨地域恢复、复杂重试或生产级身份治理。

## 生命周期阶段

### 0. 问题发现

目标：证明问题真实、目标用户明确，并找到值得验证的最小假设。

允许投入：现状观察、用户工作流、替代方案、失败成本、可证伪假设和最小实验设计。

退出证据：Human 接受目标用户、核心问题、现状基线、非目标和一条可证伪的产品假设。

### 1. 体验版

目标：让一条最小纵向切片首次产生真实可感知价值。

允许投入：完成该路径所需的最小产品语义、最小数据、最小交互、一次性适配和可复现实验证据。

保持 Deferred：通用平台、完整权限模型、HA、复杂恢复、自动扩缩容、完整 Dashboard、提前抽象的扩展体系，以及没有被当前路径使用的能力。

退出证据：真实用户在真实或足够接近真实的场景中走完整条路径，并得到可复核结果。Demo 运行、单元能力存在或架构看似完整都不能替代该证据。

### 2. 有用性验证

目标：证明体验版的价值可重复，并优于当前替代方案。

允许投入：重复实验、基线对比、产品行为指标、失败分类，以及阻止重复成功的已复现问题。

退出证据：预先约定数量的可复现实验通过；核心价值指标优于基线；Human 能指出愿意继续使用的具体收益。

### 3. Dogfood

目标：让产品在持续真实使用中保持可用，并暴露主要失败模式。

允许投入：由真实失败频率和影响排序的恢复、诊断、兼容性和操作改进；最小维护流程。

退出证据：在约定周期和工作量下持续使用；主要失败类型、发生频率、恢复成本和剩余风险都有证据；产品不依赖开发者日常救火才能运转。

### 4. 发布准备

目标：让明确范围内的其他用户能够安全安装、理解、使用和退出。

允许投入：与发布范围匹配的认证授权、数据保护、迁移恢复、兼容性、安装升级、用户文档、支持和运行观测。

退出证据：发布范围、支持承诺、风险、回滚和数据处置均明确；目标用户无需作者陪同即可完成核心路径。

### 5. 持续维护

目标：以可接受的 Human 成本持续交付价值。

允许投入：由使用数据驱动的功能演进、可靠性、成本控制、依赖升级、安全响应、兼容策略和淘汰机制。

退出条件：产品进入下一代替代、维护成本长期超过价值，或核心用户需求消失，由 Human 决定转入 Legacy。

### 6. Legacy 与关闭

目标：停止无收益演进，保留仍有决策价值的知识，并降低持续维护负担。

允许投入：关闭说明、迁移路径、必要的数据导出、仍被使用部分的最小修复，以及有当前需求证据的单位能力抽取。

项目不因“可能复用”而持续维护。没有现存用户、引用或可验证复用价值时，Human 可以删除工作副本或仓库；Git 历史、归档和必要的 durable decisions 按关闭计划处理。

## 投资判断

对每项新增能力、抽象、依赖或基础设施，Agent 必须回答：

1. 它服务哪个当前阶段退出证据？
2. 没有它，当前纵向切片具体在哪里无法完成或无法验证？
3. 这个问题已经被观察到，还是只是假设未来可能发生？
4. 能否用更小、可丢弃的方式获得同样的产品证据？

只有前两项有具体答案，或第三项已有阻断性证据时，工作才进入当前计划。其余内容进入 Deferred Decision Register，并记录重新进入条件。

## 迭代这份共识

一次项目得失先记录在所属 Initiative。只有某条经验跨项目重复出现，或现有规则持续诱发同类错误时，才更新本共识。

更新时必须说明：

- 哪个可观察问题需要改变 Agent 行为；
- 修改影响哪些生命周期阶段；
- 新规则如何改变工作准入或退出证据；
- 哪条旧规则被替换，避免同一要求出现多个事实源。

完成标准：任一 Agent 读取阶段声明和本共识后，都能判断当前应该推进、修复、推迟或停止哪些工作，并能用当前阶段证据解释该判断。
